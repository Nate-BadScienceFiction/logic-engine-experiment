What these cases test

These 21 cases check basic promises I need the engine to keep before I build more game behavior around it: draw the expected conclusions from facts and rules, preserve the information in an answer, keep a caller's edits from changing later answers, and make errors and unfinished searches visible.

Each case gives both engines the same small program and queries or operations, judged by the same expected behavior. That lets me compare what a caller actually gets from two different implementations, separately from their own unit-test suites. The case definitions record the inputs and expected behavior.

Why the results matter

The rewrite retains all six successes on reasoning and finite recursion while fixing failures in arithmetic, data handling, and isolation between returned answers. Those fixes address ways a game could keep running while making decisions from missing or altered information. The distinct-values example and returned-answer check show two of those problems directly.

Even with both timeout cases removed, the rewrite passes 16 of 19 checks, compared with 10 for the earlier engine. That gives me a concrete reason to keep developing it: fewer known failures in the behaviors game code depends on. It also exposes a loss: one explanation check passes in the earlier engine and fails in the rewrite. These selected cases establish specific improvements and a remaining gap; broader coverage and development pace still need to be measured.

How cases are counted

Pass
The comparison script accepts the outcome under that case's rule. For an answer check, the returned values must match the expected values, including order or repeated answers when specified. Other cases expect an error, check that explanation predicates answer a valid probe and reject an invalid one, or check that changing a returned list does not affect later queries. The two unbounded-search cases allow a timeout during the query; both new-engine results used that rule in this run.
Fail
An observed result violates the case's rule: for example, an answer is missing, an invalid query silently returns no answers, or an explanation predicate answers the negative control.
Unassessable
The comparison script cannot judge the case, for example because an expected-result source is unavailable or a worker produces no usable result. There were no unassessable cases in this run.
