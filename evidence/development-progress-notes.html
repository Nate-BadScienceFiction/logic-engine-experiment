The measured differences

  • Eight more passing checks: 18 − 10 = 8, or 38.1 percentage points on this 21-case set. Failures fall from 11 to 3: (11 − 3) / 11 = 72.7% fewer failing cases. This is a description of these selected checks.
  • The advantage remains without timeout allowances: excluding both unbounded-search cases gives 16/19 for the rewrite and 10/19 for the earlier engine. The difference is six passing checks, or 31.6 percentage points.
  • The first rewrite already has most of that result: 17/21 overall and 16/19 without the two unbounded-search cases. Its only later pass gain in this corpus is an open generator changing from a RecursionError to an external query timeout. The case permits that timeout; this does not demonstrate that the engine reports an incomplete search itself.
  • The sampled earlier engine improves too: 8/21 on May 8, 9/21 on June 14, and 10/21 on August 30. The two observed gains are left recursion and combining facts and rules. The sample endpoints are about 114 calendar days apart. These checks do not cover all the other work done during that period.

Why this is not a speed multiplier

  • No comparable effort denominator. I found no project-wide record of active human hours, agent hours, or API cost for both approaches. Commit counts, lines changed, and calendar gaps do not supply one.
  • The earlier repository begins with existing work. Its first source import already includes an engine and a long test history. February 2026 is not its development start. The rewrite also benefits from the earlier requirements, models, tests, and mistakes.
  • Scope and tests differ. The migration map records omitted and deferred responsibilities. Raw unit-test growth also mixes new engine checks with harness tests. The three remaining comparison failures concern explanations, including one capability the earlier engine passes.
  • The cases were selected with knowledge of both implementations. They are not an independent or random sample. Sparse snapshots of the earlier engine can miss intermediate gains or regressions. A flat count on this set does not mean no other progress was made.

To measure pace going forward, I would freeze an independent set of behavior targets before each work period, record active human and agent time and cost, and count targets met while retaining earlier passes. A fair strategy comparison would also need matched scope and comparable starting knowledge. This replay is a useful baseline for that work.

Tools and version records

The replay script uses the worker, oracle, and scoring functions unchanged from harness revision 9be7804c933cc8a3c51af3d8a5e4f54b012c8be6. It runs each engine snapshot in its own fresh local clone, each case in a separate process, with the original timeouts. SWI-Prolog expectations are obtained once and reused for all snapshots. Both published endpoints reproduce every verdict in the September 24 comparison, including reasons, answer rows, and completeness flags.

The revisions were selected before replaying: all five commits that changed the rewrite's src tree, plus its published endpoint; the earlier engine's first compatible import layout on May 8, then the last commit of each month through August. Earlier package layouts cannot be tested by this unchanged adapter and are outside this sample. Different sampling densities are explicit; this is not a search for the earliest passing old revision.

The run used Python 3.12.10 and SWI-Prolog 10.0.2 on Windows. The raw replay includes every worker result, pass/fail/unassessable decision, timeout marker, commit timestamp, source-tree identity, script hash, and expected answer. The case corpus and outcome definitions explain what a pass means.

The graph is generated from that replay with this Matplotlib script. Standalone versions: SVG and PNG.

Commands for reproducing the measurements

From a local checkout of this website repository, with Python 3.12+, Git, SWI-Prolog 10.0.2, and both engine repositories available locally, run:

python evidence\replay-development-progress.py --old-repo C:\path\BadScienceFiction-CyclopsStorm --new-repo C:\path\AkiyaBlocks-CyclopsStorm --work-dir C:\temp\cyclops-replay --output C:\temp\cyclops-replay.json --swipl "C:\Program Files\swipl\bin\swipl.exe"

Choose a new scratch directory and output file outside both input repositories. The script makes and retains its own clones; it does not change the input checkouts. The listed revisions must exist locally. Compare snapshot counts and case verdicts with the saved JSON; environment details and measurement timestamps may differ.

For the original two-version comparison, check out the earlier engine at e62758c23f66b26fa92c6d2dafaaf6bf3466499f and the rewrite at 9be7804c933cc8a3c51af3d8a5e4f54b012c8be6 in separate working copies. With the repositories side by side, run from the rewrite:

python scripts\compare_implementations.py --output artifacts\comparison\reproduction

For other locations, pass --old-root, --new-root, and --corpus explicitly. The harness documentation describes the complete comparison.
